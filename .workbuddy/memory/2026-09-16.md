## P3-1 任务规划器最小切片落地（commit `b6db89ae3`）

按审查报告 P3-1 推进"未来 Agent"主线。差距分析后选定的**最小可交付模块**是"任务规划"，
因为它是 3.2 差距矩阵里唯一标 ❌ 的**结构性缺失**（规划完全交给模型工具调用，仓库无 Planner 组件），
且它依赖的 P2-1（策略外置）已完成、P2-4（maxSteps）本就已可配。

### 新增文件（kernel）
| 文件 | 职责 |
|---|---|
| `domain/agent/plan/TaskPlan` | 规划结果，不可变；`withStepStatus` 返回副本（记录快照不会读到半改状态）。`toJson()` **刻意不含 goal 与步骤正文**——手写拼装无转义，会进 trace/运行步骤 |
| `domain/agent/plan/PlanStep` / `PlanStepStatus` | 步骤 + 状态枚举；`dependsOn` 表达"可并行"（依赖同一步骤的两步无先后约束） |
| `domain/agent/plan/TaskPlanningRequest` | 规划入参（目标 + 身份 + 步数上限），不传消息历史/工具清单 → 纯函数式便于替换 |
| `policy/TaskPlanningPolicy` | 纯 Java 载体：enabled(false)、maxSteps(5)、顺序/并行标记词（中英分表）。沿用 P2-1 的 `kernel/policy` + autoconfigure 绑定模式，kernel 零 Spring |
| `ports/outbound/agent/TaskPlannerPort` | 规划唯一入口，方便后续换 LLM 规划器 |
| `application/agent/plan/DefaultTaskPlanner` | 确定性切分：编号（`1.`/`2、`/`第一步…`）→ 顺序标记 → 强分隔符；命中并行标记则**继承前一步依赖**；超步数上限时**合并尾部**而非丢弃 |
| `application/agent/AgentLoopPlanner` | 主循环的规划协作类（trace + 运行步骤 + 状态推进 + 提示词注入） |
| `application/agent/AgentLoopDegradedAnswer` | 降级答案渲染从主循环搬出 |

## 后续 4 项全部落地（commit `642448b7c` / `b531dcbd4` / `c75ca06f6` / `e6f7267c1`）

### ① LLM 语义分解规划器 `642448b7c`
- **模型只"改写"目标、不产出规划结构**：`LlmTaskPlanner` 让模型把目标重写成编号步骤，
  再把这段文本喂给 `DefaultTaskPlanner` 解析。避免模型自由文本/markdown 直接成为 PlanStep。
- 模型端口只有流式 API → 内部类 `Collector`（`StreamCallback` + `CountDownLatch`）做同步阻塞封装，
  与 `TurnBuffer` 同一手法；超时则 `cancel()` 流并回退。
- 回退面很宽：模型不可用 / 抛异常 / 输出为空 / 解析后 ≤1 步，**一律对原始目标**回退确定性切分。
- `PlannerMode` 默认 `HEURISTIC`；`LLM_WITH_HEURISTIC_FALLBACK` 且 `modelPort != null` 才启用。
- 踩到的小坑：`DefaultTaskPlanner` 里有一处 `new TaskPlanningRequest("", null, null, null, null, 0)`
  的守卫构造（6 参），加 `modelId` 变 7 参后要同步。

### ② 真正并行调度 `b531dcbd4`
- 新增纯函数 `TaskPlanScheduler`（拓扑分层 → `List<PlanWave>`）+ `AgentLoopParallelTurns`（并发发轮次）。
- **关键取舍：只并行"发问"，不并行"落地"。** 工具执行、观察回灌、事件发送、trace、状态记账
  仍由主线程按波次顺序完成 → 工具网关 / 流式发射器 / trace 记录器**都不需要变成线程安全的**，
  并行失败也保持串行语义（任一步失败即把原始异常抛回主循环）。这是能小步落地的关键。
- 环、未知依赖 → 安全降级为串行。默认关闭（`parallel-steps=false`）。

### ③ checkpoint 续跑 `c75ca06f6`
- 新增 `AgentCheckpointType.STEP_BOUNDARY`；`AgentLoopCheckpoints` 读写续跑状态。
- 语义澄清：`maxSteps` 本是"单次调用的推理预算"，事实却成了"任务总时长上限"。
  续跑后每次调用都拿到一整份新预算，长时程任务可跨多次调用完成。
- 写入失败只记日志；读取失败（无检查点 / JSON 损坏 / schema 不匹配）**一律退化为从头开始**——
  绝不让"续跑"比"重跑"更糟。落盘沿用审批检查点的凭证脱敏约定。

### ④ 自学习闭环 `e6f7267c1`
- `LearningSignal` / `PolicyAdjustmentProposal` / `PreviousProposalOutcome` / `LearningLoopReport`
  （领域层）+ `KernelLearningLoopService`（应用层）。**未新增任何仓储或端口**，聚合与判定全是纯计算。
- 闭环：点踩与人工复核 → 按目标聚合为信号 → 产出带证据的建议 → 人工决定落地 →
  用评测通过率回访上一次改动（改进/回归/不足以判定）。
- **刻意不做自动执行器**：阈值一改流量分布立刻变化，而反馈信号要几天才追得上，自动改等于震荡。
- 数据粒度如实说明：反馈与复核之间目前只有 `userId` 是共有字段，故分别在"反馈原因"与
  "记忆 targetKey" 维度聚合，再叠加全局聚合。

### 横切教训（复用价值高）
- **`KernelAgentLoop` 的 700 行 / 单构造函数预算是每次加功能的硬约束。**
  这次连续三次靠"先抽走既有代码"腾空间：`AgentLoopDegradedAnswer`(667) →
  `AgentObservationText`+`AgentLoopStreamEvents.asToolEvents`(690) → `AgentLoopRunRecorder`(657)。
  **顺序固定：先抽既有、再加新，不要动守卫。**
- 每加一个功能都配一个**默认关闭开关**，并在提交信息里写清"默认路径行为与引入前完全一致"。
- Item 4 未新增端口 → `complexity-baseline.txt` / `cross-domain-whitelist.txt` 无需改动，
  architecture-tests 仍 16/16。

## 第二轮 4 项：收益验证 / 并行安全 / 信号对齐 / 落地工单

按用户确认的顺序实施：④ 信号对齐 → ① 基准 harness → ② 并行前置改造 → ③ 落地工单。

### ④ 信号对齐 `267b7d353`
- 真正的共有维度是**会话**（sessionId = conversationId），两侧源数据本就存在，是传递链漏接
  （`MemoryReviewRecord` 有 conversationId，`MemoryReviewFeedbackSample.fromDecision` 没拷）。
- **runId 在记忆捕获点不可得**：`MemoryCaptureStage:141` 只拿到 `StreamChatContext`（无 runId）；
  且 `t_memory_review_candidate.message_id` 是 VARCHAR、`t_message.id` 是 BIGINT，
  agent 路径下该字段存的还是流任务 id → **JOIN 反查不可靠**。宁可留空，也不造一个
  看起来对齐、实际对不上的维度。
- 会话信号**只进报告、不进全局汇总**（否则每条样本被数两遍），也不产生建议（会话是一次性的）。
- 兼容构造：`MemoryReviewFeedbackSample` 加 20 参重载，18 处既有调用点无需改动。
- **"对齐"不只是加列**：`KernelLearningLoopService` 原本反馈按 reason、复核按 targetKey 聚合，
  两者根本没有共有维度，必须新增按 sessionId 的聚合路径才叫对齐。

### ① 基准 harness `6c9ea8df8`
- 放 `kernel/src/test/.../agent/bench/`：golden 仓储（`_index.json` + `regression.json`，32 例）
  + `ScriptedModel` + `AgentLoopBenchmarkHarness` + 报告写出器。
- 绕开"四开关是全局单例"的办法：**每臂独立构造 `KernelAgentLoopOptions` + `KernelAgentLoop`**。
- 判据四条同时满足才算收益明显：完成率 ≥+5pp、token ≤+30%、步数/工具调用不劣化 ≤+10%、
  配对 McNemar p<0.05 且不一致样本 ≥10。
- 实测：**A4 checkpoint 续跑收益明显**（37.5% → 100%，token +10.3%，p<0.0001）；
  A1 确定性规划未达阈值（+0.0pp / token +63.8%）；A2/A3 脚本桩评不出语义收益，只验管道。
- 断言的是"harness 可信"（用例量够、基线确实截断、续跑确实发生、并发确实 ≥2），
  **不是"某臂一定赢"**——后者是实验结论，写死成断言只会把基准变成摆设。
- 踩坑：续跑循环一度被套用到所有臂，把"截断"这个关键观测值抹掉了；
  脚本桩的规划响应原本没有并行标记词，导致并行臂根本无从触发。

### ② 工具并行前置改造 `3c88add69`
- **前提更正**：工具执行的并行能力一直存在（`AgentLoopToolExecutor:102` 按 `maxParallelTools`
  分批 + `invokeAll`），只是默认 1 而退化为串行。本次是"调大默认值前先修隐患"，默认值仍为 1。
- 三条真隐患：
  - 取消后剩余批次仍执行——原实现只看主线程中断标记；而 `AgentRunControl` 会把新线程池立刻
    `shutdownNow`，`invokeAll` 在 execute 阶段抛 `RejectedExecutionException`，
    **"用户取消"被伪装成"工具执行失败"**。已在执行中的那个无法撤销，照常返回成功。
  - `RepositoryAgentRunStepRecorder.nextStepNo` 是 read-then-write，非原子 → 加锁成一步。
  - `LocalChatStreamCallback`：并行波次下多个模型流共享同一个 callback，
    `answer`/`thinking` 是 StringBuilder、`currentRunId` 等是普通字段 → StringBuffer + volatile。
    内容仍会交错，那是产品语义问题，本改动只解决内存安全。
- `KernelAgentLoop:471` 的"各步骤节点会被并发写坏"注释**已过时**：`KernelRagTraceRecorder`
  只有 final 字段、无 ThreadLocal 与节点栈，`TraceNodeScope` 不可变，JdbcTemplate 实现无状态。
- **前置实测**：临时把内核与 autoconfigure 默认值调到 4 跑全量 → 内核 1072 项全通过；
  集成测试的失败全是环境依赖（E2E 需 docker 后端、NativeAdapter 需 Milvus），未复现并发问题。
  实测后默认值已还原。

### ③ 落地工单 `983d790b6`
- 独立建 `sa_policy_adjustment_ticket` + 独立状态机
  （PENDING → APPROVED/REJECTED → APPLIED → ROLLED_BACK），只复用审批的"乐观更新"模式。
- **指纹去重只取"配置键 + 方向 + 目标"**：不认可率与样本量每轮都在变，进了指纹永远去重不掉。
- 状态迁移 `UPDATE ... WHERE status = ?`，并发失手抛错让人重载——工单可被多人审批，
  先读后写会让后一个人的决策静默覆盖前一个人的。
- proposal → ticket 转换放应用服务，domain 保持纯数据载体不碰 IO。
- 基线：+2 outbound / +1 inbound → 355→358 / 261→263 / 93→94；R3 白名单无需新增条目。

### 可复用经验
- **改"默认值"之前先做一次临时调值的实测**，能区分"理论隐患"与"真会复现的问题"；
  同时能识别哪些集成测试其实是环境依赖（Milvus / docker），避免误判为回归。
- **surefire-reports 目录会残留历史报告**，汇总失败数时必须按时间戳过滤，
  否则会把上一次运行的失败算进本轮。
- 涉及"聚合维度"的需求，先确认**数据里到底有没有这个维度**，再决定是加字段还是改聚合逻辑。
- 前端补页面前先找**同类型既有页面**当模板（本项目是审批中心），并确认：
  端点清单是否生成式、路由/菜单/面包屑三处是否都要登记、功能开关从哪来。
- Radix 的 `AlertDialogAction` **点击默认会关闭弹窗**，表单校验失败的错误提示根本来不及显示；
  需要 `event.preventDefault()` 拦下默认行为，成功路径再自行关闭。
- 前端"某状态可执行哪些动作"的表要与后端状态机枚举保持一致，否则会给出点了必错 400 的按钮。
- 新增的可选依赖若走 `ObjectProvider.getIfAvailable(...::empty)` 兜底，
  要补一个"不提供任何端口"的 ApplicationContextRunner 测试——缺 bean 只会在生产启动时炸，
  单测与控制器 slice 测试都覆盖不到。
