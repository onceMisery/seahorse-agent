## 一、过度设计：哪些抽象层在为抽象本身服务

### 1.1 端口接口的数量与实现分布（关键证据）

对 `kernel` 下所有 `*Port.java` 逐一判定"是否为真接口"，再全仓统计其实现类分布：

| 指标 | 数量 | 占比 |
|---|---|---|
| 真接口总数 | **354** | 100% |
| ├ 出站端口 outbound | 254 | 71.8% |
| ├ 入站端口 inbound | 93 | 26.3% |
| └ 其他 | 7 | 2.0% |
| 唯一实现接口（初版口径，见下方更正） | 147 | 41.5% |
| 唯一实现且该实现在 kernel（初版口径，见下方更正） | 84 | 23.7% |

> ### ⚠️ 统计口径更正（2026-09-15，落地复核时发现）
>
> 上表后两行、以及原报告给出的"22 个零实现接口"结论，**统计方法存在缺陷，不能作为删改依据**。
>
> 初版使用 `Select-String` 按行匹配 `(class|record|enum)\s+\w+[^{]*implements[^{]*\{`，
> 这会漏掉**跨行书写**的 implements 子句，也会漏掉**非 implements 形态**的实现供给方式。
> 复核发现本项目的端口实现大量采用以下形态：
>
> - 静态工厂方法：如 `ModelContextWindowPort.strictConfigured(...)` 在
>   `SeahorseAgentKernelAgentAutoConfiguration` 中直接产出实例，全文无 `implements` 字样；
> - 匿名类 / lambda：`new XxxPort() { ... }`；
> - 跨行 implements 列表。
>
> 因此"零实现"是**假阳性**。经复核，`ModelContextWindowPort` 等接口虽无 implements 子句，
> 却被 `AgentLoopDependencies`、`AgentLoopModelTurns`、`ModelContextEnvelopeBuilder`
> 等核心链路实际依赖——若按初版结论删除，将直接破坏 Agent 主链路。
>
> **结论：354 这个总数可用；"22 / 147 / 84" 需在下述更严谨口径下重算后才能作为重构依据。**
> 更严谨口径应同时统计：implements 子句（跨行）、`new Xxx(` 匿名实例化、返回该类型的静态工厂、
> 以及返回该类型的 `@Bean` 方法。本报告已据此撤回 P0-3。

典型形态：

```
SeahorseDashboardController  →  DashboardInboundPort  →  KernelDashboardService
SeahorseAuditController      →  AuditLogInboundPort   →  KernelAuditService
SeahorseAuthController       →  AuthInboundPort       →  KernelAuthService
```

93 个 `*InboundPort` 中绝大多数是这种 1:1 直通——Controller 完全可以直接注入 `KernelXxxService`，
Spring 本身就是最好的"入站端口"。**真正需要入站端口的地方是有多种调用协议以上（REST + SSE + MCP + MQ）的业务，
这类端口目前不足 5 个。**

#### 关于"零实现接口"（已撤回）

初版曾列出 22 个所谓"零实现接口"并建议删除，**该结论已撤回**。复核结果：
这些接口虽无 `implements` 子句，但都在被真实引用，实现由静态工厂 / lambda / 匿名类供给。
例如 `ModelContextWindowPort` 由 `ModelContextWindowPort.strictConfigured(...)` 产出，
被 `AgentLoopDependencies`、`AgentLoopModelTurns`、`ModelContextEnvelopeBuilder` 依赖——
属于 Agent 主链路，删除会直接破坏构建与运行。

**遗留的真问题（与"零实现"无关）**：README 的适配器矩阵与部分文档暗示了模型治理、
发布订阅等能力，读者难以判断其就绪程度。建议改为在文档中标注每个端口的
"已实现 / 仅配置占位 / 规划中"状态，而不是删除代码。

### 1.2 空壳 Noop 与其引发的二次复杂度

| Noop 实现 | 行数 |
|---|---|
| `adapter-vector-noop/NoopVectorStoreAdapter.java` | 81 |
| `adapter-observation-noop/NoopObservationAdapter.java` | 54 |
| `kernel/.../NoOpQueryRewriteAdapter.java` | 39 |
| `kernel/.../NoopObservationPort.java` | 47 |
| `kernel/.../NoopAgentRunEventBuffer.java` | 46 |
| `kernel/.../ports/common/NoopFallback.java` | 38 |

> 注：`NoopFallback` 是一个 marker 接口，被嵌套在多个 Port 文件内部的 `Noop*` 实现使用
> （如 `MemoryVectorPort.NoopMemoryVectorPort`、`MemoryGraphPort.NoopMemoryGraph`
> 、`MemoryOutboxPort.NoopMemoryOutbox`、`ToolInvocationAuditPort.NoopToolInvocationAudit` 等）。
> 也就是说"每个 Port 文件自带一个空实现"已成为一种内建惯例。

真正说明问题的是这套 Noop 机制**还额外养出了一个守卫 + 一个测试**：

```
autoconfigure/SeahorseAgentNoopPortGuard.java        231 行
tests/SeahorseAgentNoopPortGuardTests.java           364 行
```

**为了不让 Noop 实现泄漏到生产，专门写了 595 行代码来防守因为引入 Noop 而产生的风险。**
这是"用复杂度治理复杂度"的典型：如果一开始不用 Noop 兜底（改为启动时缺失依赖即 fail-fast，
或把 demo 模式的空实现放到单独的 demo 模块），这 595 行本不需要存在。

且这与 `CONTEXT.md` 自己写下的原则相冲突：

> **显式功能禁用**：对不可用能力返回稳定且可诊断的禁用结果，而不是空数据、伪成功或无证据的自动降级。

Noop 兜底恰恰是"返回空值也算成功"。

### 1.3 从未被生产代码调用的 PortWrapper 机制

README 的架构图把它列为横切治理能力：

> | 横切治理 | `PortWrapper`/`PortWrapperChain` | 限流、重试、熔断、审计等横切关注点 |

实际调用点统计（排除 node_modules / target / .worktrees）：

| 模式 | 出现次数 | 命中位置 |
|---|---|---|
| `new PortWrapperChain` | **5** | 其中 2 处在 `PortWrapperChain.java` 自己内部，3 处在 `PortWrapperChainTests.java` |
| `PortWrapperChain.` | 12 | 全部在 `PortWrapperChain.java` 与 `PortWrapperChainSnapshot.java` 自身定义中 |

**结论：`kernel/plugin/wrapper/` 整个包（9 个类：`PortWrapper`、`PortWrapperChain`、
`PortWrapperChainSnapshot`、`PortWrapperDiagnostic`、`RetryPortWrapper`、`CircuitBreakerPortWrapper`、
`RateLimitPortWrapper`、`AuditPortWrapper`、`ObservationPortWrapper`）生产调用点为零，只有自测试和自引用。**

Spring AOP + Resilience4j / Micrometer 能直接覆盖同类诉求，且自带生态与运维工具。
这是一处明确的超前设计：文档里它是"平台治理能力"，代码里它是"没接线的预留插槽"。

### 1.4 自研插件框架 ExtensionRegistry

`DefaultExtensionRegistry` 是 `ExtensionRegistry` 在生产中的唯一实现，
在 `SeahorseAgentKernelPluginAutoConfiguration.java`（320 行）中注册了 **17 个扩展**：

```
FeatureType.INGESTION_NODE               × 10
FeatureType.SEARCH_CHANNEL               ×  3
FeatureType.SEARCH_RESULT_POST_PROCESSOR ×  4
```

这套机制确实在用（区别于 PortWrapper），但它在重复 Spring 已经免费提供的事：
`List<T>` 按类型注入 + `@ConditionalOnProperty` + `@Order` + `@ConditionalOnBean`
能等价实现"注册—排序—按配置启停"。当前实现额外带来了：
`ExtensionDescriptor` / `ExtensionRegistration` / `ExtensionLoadDiagnostic` /
`FeatureActivationContext` / `FeatureHealth` / `FeatureHealthReport` / `FeatureType` /
`AgentFeature` / `AgentSPI` / `AgentExtension` 共 10 个配套类型。
**收益（一个 Set）远小于成本（一套元模型 + 新成员学习成本）。**

### 1.7 小结：过度设计的边界在哪

**公平地说，不是所有抽象都是坏的。** 出站端口中确实存在真·多实现的健康抽象：

| 能力 | 可替换实现 | 判定 |
|---|---|---|
| 向量库 | milvus / pgvector / noop | ✅ 抽象成立 |
| 关键词检索 | elasticsearch / lucene | ✅ 抽象成立 |
| 缓存 | local / redis | ✅ 抽象成立 |
| 消息队列 | direct / pulsar | ✅ 抽象成立 |
| 对象存储 | local / s3 | ✅ 抽象成立 |
| 观测 | micrometer / noop | ✅ 抽象成立 |
| 解析 | tika | ⚠️ 单实现，但符合"可换解析器"预期 |

**问题集中在三处**：
1. **入站端口层（93 个）**——形态上多为 `Controller → XxxInboundPort → KernelXxxService` 的 1:1 直通，
   Spring 本身已提供等价能力。⚠️ 但"其中 84 个唯一实现在 kernel"这一量化证据来自有缺陷的统计口径（见 1.1 更正），
   动工前需按更严谨口径重算，并按业务逐个判断是否真的存在多协议入口；
2. **自研框架层（PortWrapper 9 类 + ExtensionRegistry 10 个配套类型）**——与 Spring 原生能力重叠且前者零生产调用；
3. **Noop 兜底层**——为"降级"付出的额外守卫复杂度。

### 2.2 典型案例 A：所谓"语义路由"其实是中文关键词 contains

`缺少的功能.md` 第 2 条把"语义引导或语义路由：引导式问答歧义判断及 LLM 确认机制"列为**尚未实现**。
但代码里已经有了"路由"，只是实现方式是字符串包含：

`kernel/application/memory/DefaultMemoryRouter.java`（81 行，22 个中文字面量）

```java
boolean correctionQuestion = containsAny(question, "不是", "错了", "改成", "以后别", "忘记")
        || containsAny(lower, "not anymore", "wrong", "correct", "change to", "forget");
boolean businessQuestion = containsAny(question, "知识库", "文档", "规则", "制度", "流程", "阈值", "接口", "API")
        || containsAny(lower, "knowledge", "document", "policy", "rule", "process", "threshold", "api");
boolean episodicQuestion = containsAny(question, "上次", "之前", "历史", "项目", "决策", "讨论过", "做过",
        "长期记忆", "记忆", "记得")
        || containsAny(lower, "last time", "previous", "history", "project", "decision",
        "discussed", "remember when", "long-term memory");
```

**影响**：
- 用户说"我记得之前那条规则"路由成功；用户说"先前的那个约定呢"路由失败——**召回是否命中取决于用户用的词是否恰好落在写死的 23 个词表里**；
- 换行业（如从医疗到金融）必须改 Java 代码重新发版，**多租户无法各自配置**；
- 英文/混合语种行为与中文不一致；
- 无法做 A/B：想调这个词表只能重新编译部署。

### 2.3 典型案例 B：所谓"记忆抽取与画像"其实是正则 + 写死置信度

### 执行顺序建议

```
P0（1–2 周）──► P1（3–6 周）──► P2（4–8 周）──► P3（季度级）
  去噪止血        拆除假抽象        规则数据化        接自治主线
```

**不要跳过 P1 直接做 P2/P3。**
理由很简单：在一个有 355 个接口、其中 84 个是自我转发的系统上叠加"规划器"和"自学习闭环"，
每加一个能力就要先穿透三层无用间接才能落地；
而先把假抽象拆掉，同样的工作量能直接作用在业务语义上。

另外，P0-1/P0-2 建议在动手前先建立一次干净的 tag，确保清理 worktree/stash 时可回滚。
